01 the problem

The chapter runs on Discord, but the data that mattered lived everywhere else.

members

  • Joined the server, filled out a form, then waited for an officer to assign their role by hand.
  • Had no way to see their own points or where they stood.

officers

  • Took attendance on sign-in sheets and tallied points in spreadsheets after every event.
  • Kept a Notion member directory that drifted out of sync with who was actually in Discord.

The real cost wasn't any single task. It was that nobody trusted the numbers, so points and attendance got re-checked by hand.

02 users & research

I talked to [#] officers and [#] members before writing code, then kept talking to them between releases.

  • Officers already live in Notion. A new dashboard would be one more thing to check, so the data had to show up where they already work.
  • Members won't leave Discord. Anything that sent them to a website or a form lost people, so every flow had to happen inside the server.
  • The directory data is messy. Nicknames, typos, and personal vs. school emails meant exact matching would lock real members out.
  • Check-in has to be fast. At a packed meeting, anything slower than typing a short code would back up the room.

04 key product decisions

where the data lives

  • Notion only
  • Google Sheets
  • SQLite + Notion sync

Why: Notion's API is rate-limited and slow, so writing every check-in straight to it would stall during a busy meeting. SQLite gives the bot instant local writes, and a sync layer mirrors everything into Notion, where officers already work.

Tradeoff: two copies of the data means sync logic. That's where the race condition came from (see architecture).

how strict verification should be

  • exact email match only
  • officer approves everyone
  • exact match → fallback match → officer review

Why: exact matching locked out real members with messy records, and manual approval doesn't scale past a few dozen people. A matching cascade verifies most members instantly and only sends the true edge cases to an officer.

how members check in

  • react to a message
  • scan a QR code
  • officer-generated check-in code

Why: a reaction can be clicked from anywhere, and QR needs a screen at every event. A short, time-limited code read out in the room proves you were there and works for hybrid events too. QR is on the roadmap as an add-on, not a replacement.

who can do what

  • hardcoded officer IDs
  • one admin role
  • member / officer / admin tiers mapped to Discord roles

Why: officer boards turn over every year. Tying permissions to roles means a handoff is just reassigning roles, with no code changes and no redeploy.

05 technical architecture

Two layers on purpose: SQLite handles speed and correctness, and Notion handles visibility. The bot never waits on Notion to answer a member.

the sync race condition for engineers

Early on, two things could touch the same member at once: a check-in awarding points and the sync worker pushing that member to Notion (or two check-ins landing together). Both read the row, both computed a new total, and whichever wrote last won, so points silently disappeared.

The fix was a per-member asyncio.Lock around every read-modify-write, plus a version number on each row. The sync worker takes the same lock, snapshots the row, pushes it to Notion, and only clears the dirty flag if the version hasn't changed since it started.

async with locks[member_id]:
    row = db.get(member_id)
    row.points += award
    row.version += 1
    row.dirty = True
    db.save(row)
identity verification for engineers

New members get a persistent "Get Verified" message. It's registered as a persistent view, so the button keeps working across bot restarts and redeploys. Clicking it opens a modal for name and email, then the matcher runs:

  1. exact email match against the directory
  2. normalized fallback: lowercased, trimmed, school vs. personal email, name similarity
  3. no confident match: queue it for an officer with the closest candidates attached

A match assigns the Member role and class-year role automatically and links the Discord ID to the directory row.

permissions design for engineers

Every command declares a minimum tier: member, officer, or admin. A single check maps the user's Discord roles to a tier before the command runs, so officer commands like starting attendance or adjusting points are invisible to members. New officers get access the moment their role changes.

deployment for engineers

Containerized with Docker and deployed to Fly.io for 24/7 uptime, with the SQLite file on a persistent volume and secrets (bot token, Notion key) kept in Fly's secret store. Shipping a change is one deploy, with no laptop that has to stay on.

06 execution & iteration

I shipped small, watched how officers and members actually used it, and changed course based on what club leadership told me.

  1. v1
    verification + roles. Linked Discord to the directory and auto-assigned roles. Learned: exact matching failed on messy records.
  2. v2
    fallback matching + officer review. Most members verified on the first try, and leftovers went to a short officer queue.
  3. v3
    attendance codes + points. One officer command per event, members type the code, points land instantly. Learned: writing straight to Notion was too slow at busy events.
  4. v4
    SQLite + Notion two-layer sync. Instant check-ins, with Notion as the readable view. Fixed the sync race condition with locks.
  5. v5+
    points by event type, leaderboard, role tiers. Different events earn different points, members can check their standing anytime, and officers got a screen-capture tutorial for the attendance flow.

08 what's next & what i learned

roadmap

  • QR code check-in as an option for big events
  • automated event reminders and announcements
  • an officer analytics view in Notion (attendance trends, at-risk members)
  • handoff docs so the next officer board can own it

lessons

  • Talk to users first. The Notion-only design would have failed at the first big meeting.
  • Design for messy real-world data instead of the clean data you wish you had.
  • Boring tech wins: SQLite plus a lock fixed what a fancier stack would have hidden.
  • Ship small, and let feedback set the next version.
